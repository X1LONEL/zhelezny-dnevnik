# Железный дневник

Веб-приложение для записи силовых тренировок и питания по персональной
9-недельной программе одного человека (владелец репозитория).

Живёт в двух видах, из одного исходника:

1. **Artifact на claude.ai** — данные в облачной базе артефакта, дневник
   открывается с любого устройства, но нужны сеть и вход в аккаунт.
2. **Устанавливаемое приложение (PWA)** на GitHub Pages — ставится на
   домашний экран iOS, работает без сети, данные только на этом
   устройстве. Синхронизации нет, перенос — через резервную копию.

Интерфейс и весь код-комментарий — на русском. Пиши так же.

## Запуск

```
npm run build     # собрать dist/ (оба выхода: артефакт и PWA)
npm run check     # только проверить: порядок CSS и синтаксис JS, без записи
npm test          # слияние с облаком, резервная копия, прогрессия
npm run serve     # отдать dist/pwa на http://localhost:8080
open dist/index.html   # посмотреть локально в браузере
```

**PWA нельзя проверять через `file://`.** Браузер не регистрирует service
worker вне http/https, а без него нет ни офлайна, ни установки — страница
откроется, но офлайн-режим останется непроверенным. Для проверки:
`npm run serve`, затем `http://localhost:8080` (localhost считается
защищённым контекстом, HTTPS для него не нужен).

Зависимостей нет, `npm install` не нужен — сборка это один `build.mjs`
на голом Node.

## Как устроена сборка

`src/` разбит на файлы, `build.mjs` склеивает их в один самодостаточный
HTML в порядке из `src/manifest.json`.

```
src/manifest.json   порядок склейки: styles → markup → scripts
src/styles/*.css    одна таблица стилей, разрезанная по разделам
src/markup/*.html   куски разметки, склеиваются подряд
src/js/**/*.js      обычные скрипты, НЕ модули
```

На выходе три вещи:

- `dist/artifact.html` — то, что публикуется как Artifact. **Без**
  `<!doctype>`, `<html>`, `<head>`, `<body>`: платформа оборачивает
  содержимое сама.
- `dist/index.html` — тот же код в полноценном документе для локального
  просмотра. Собирается автоматически, публиковать его не нужно.
- `dist/pwa/` — устанавливаемое приложение: `index.html`, манифест,
  service worker и четыре PNG-иконки. Это то, что уезжает на GitHub Pages.

Приложение внутри всех трёх — байт в байт одно и то же. Различается только
обёртка: у артефакта её ставит платформа, у PWA её собирает `build.mjs`.

**Скрипты склеиваются в одну область видимости.** Модулей нет намеренно:
опубликованная страница должна быть одним файлом без импортов. Отсюда
правила:

- Имена глобальны — не заводи две функции с одним именем в разных файлах.
- Порядок в manifest важен только для кода, который выполняется на верхнем
  уровне. Такой код весь собран в `boot.js`, и он идёт последним. Объявления
  функций поднимаются, поэтому взаимные вызовы между файлами безопасны.
- `const` на верхнем уровне попадает во временную мёртвую зону: файл,
  который идёт раньше, не должен читать `const` из файла, который идёт позже,
  во время загрузки.
- Директиву `"use strict"` добавляет сборщик, в исходниках её нет.

`@import` шрифтов обязан быть первым правилом итоговой таблицы стилей,
поэтому `tokens.css` всегда первый в manifest. Сборка падает, если это
нарушено.

## Ограничения платформы Artifact

Это не обычная веб-страница, и часть привычных приёмов там не работает:

- **CSP.** Внешние скрипты — только с cdnjs.cloudflare.com, внешние стили —
  только с fonts.googleapis.com. Всё остальное блокируется молча: картинки,
  fetch, XHR, шрифты со сторонних хостов. Любые свои CSS и JS — внутри
  страницы, картинки — data:-URI.
- **Тема.** Страница рендерится в теме зрителя, и состояний три: явный выбор
  ставит `data-theme="dark"` / `"light"` на корне, а системная настройка не
  ставит ничего. Поэтому все цвета живут токенами в голом `:root`
  (`tokens.css`), а тёмные значения переопределяются дважды: в
  `@media (prefers-color-scheme: dark)` под защитой
  `:root:not([data-theme="light"])` и в `:root[data-theme="dark"]`.
  Никогда не задавай цвет только внутри media-блока — он не применится в
  несоставленном состоянии.
- **Ширина.** Страница обязана работать от ~400px. Боковой отступ не меньше
  16px, горизонтальной прокрутки у body быть не должно — широкие таблицы
  оборачиваются в `.tscroll`.
- **localStorage работает**, но в артефакте это кэш на одном устройстве, не
  источник правды. В PWA — наоборот, единственный источник правды.

## Ограничения PWA

Другая площадка — другой набор граблей:

- **Артефакт установить на телефон нельзя.** Он рендерится в песочнице
  внутри claude.ai, своим `<head>` не управляет, а service worker
  регистрируется только с файла на собственном origin. «На экран «Домой»»
  из артефакта сохранит закладку на claude.ai, которая без сети не
  откроется. Отсюда и взялся отдельный выход сборки.
- **iOS ставит только растровую иконку.** `apple-touch-icon` не понимает
  SVG, а манифест телефон читает уже после установки. Поэтому PNG
  генерируются на сборке (`src/icon.mjs`, свой кодировщик на `zlib` —
  заводить зависимость ради четырёх картинок незачем). `icon-180.png`
  обязан быть ровно 180×180, иначе iOS положит на домашний экран скриншот
  страницы.
- **Все пути относительные** (`./`): и в манифесте, и при регистрации
  service worker. GitHub Pages отдаёт проект по адресу вида
  `user.github.io/<репозиторий>/`, и абсолютный `/sw.js` там указывает
  мимо. Не меняй на абсолютные.
- **Имя кэша — отпечаток сборки** (`zhd-<hash>`). При деплое старый кэш
  сносится целиком в `activate`. Если кэш назвать постоянно, телефон
  навсегда останется на первой установленной версии.
- **Навигация идёт «сеть вперёд, кэш в запас».** Иначе обновление
  доезжало бы до телефона только после ручной переустановки. Остальное
  (иконки, шрифты) — «кэш вперёд».
- **Шрифты Google в оболочку не положить**: адреса `woff2` зависят от
  браузера. Они попадают в кэш по факту первой загрузки — то есть первый
  запуск приложения обязан быть с сетью, дальше офлайн. Если понадобится
  офлайн с самого первого открытия, шрифты нужно класть в репозиторий.
- **`display: standalone` + `black-translucent`** означает, что содержимое
  уезжает под строку состояния. Компенсируется `env(safe-area-inset-top)`
  на шапке и `env(safe-area-inset-bottom)` на `.wrap`. Правишь шапку —
  проверь на телефоне с вырезом.

## Хранение данных

Две ступени, одна поверх другой.

1. **localStorage**, ключ `zhd_v1` — пишется всегда и сразу, чтобы приложение
   работало офлайн и не теряло ввод.
2. **Облачная база артефакта** (`claude.use("db")`) — включается, когда
   доступна. Схема:

```
meta/settings          { startDate }
meta/body              { entries: [{d, kg, waist, arm}] }
meta/draft             { d: <незавершённая тренировка | null> }
workouts/<id>          одна запись = одна тренировка
nutrition/<ГГГГ-ММ>    { days: { "ГГГГ-ММ-ДД": { items: [...] } } }
```

Питание агрегировано по месяцам осознанно: у базы артефакта лимит 5000
документов, а по документу на день съел бы его за 13 лет и оставил бы
тренировки без места.

Приложение обязано полностью работать, когда `claude.use("db")` вернул
`null` — это нормальное состояние, а не ошибка. Вся работа с базой в
`boot.js` обёрнута в try/catch, а строка состояния («сохранено» /
«сохранено на этом устройстве») говорит пользователю правду о том, куда
ушли данные.

Слияние при загрузке: локальные записи, которых нет в облаке, до-заливаются
наверх, а не затираются. Не ломай это — иначе тренировка, записанная в
офлайне, исчезнет при первом подключении.

Правило одно на все три раздела, ключ слияния свой: тренировки — по `id`,
вес тела — по дате, питание — по дню внутри месяца. При совпадении ключа
выигрывает облако. Чистые функции `mergeBody` и `mergeNutMonth` лежат в
`core/state.js`, на них написан `test/merge.test.mjs` — правишь слияние,
прогони `npm test`.

### Резервная копия

Синхронизации между артефактом и PWA нет и не планируется: у PWA нет
доступа к базе артефакта. Мост между ними — файл копии, кнопки в журнале
(«Сохранить копию» / «Восстановить из файла»). Это же путь переноса
истории при первой установке на телефон.

CSV рядом оставлен намеренно: он для таблиц, в нём нет ни питания, ни веса
тела, и читать его обратно приложение не умеет. Копия — весь стейт одним
JSON.

`mergeBackup` (`core/state.js`, тесты в `test/backup.test.mjs`) собран на
тех же `mergeBody` и `mergeNutMonth`, но роль «основы» играет то, что уже
в приложении: **импорт добавляет и никогда не затирает**. Копия по
определению устарела, и если дать ей выигрывать конфликт, открытый
вчерашний файл сотрёт сегодняшнюю тренировку. Не переворачивай это
правило. Заливка наверх идёт прямо из обработчика `onSnapshot`;
она не зацикливается, потому что после записи расхождения не остаётся и
следующий снимок уже ничего не отправляет.

## Откуда взялись данные программы

Всё в `src/js/data/` перенесено из PDF с персональной программой тренировок
и питания, который дал владелец. Это не абстрактный справочник, а конкретный
план под конкретного человека:

- `program.js` — каталог упражнений (`EX`), дни (`DAYS`), ротации, стартовые
  веса (`SEED_W`), пояснения к неделям (`WEEKNOTE`).
- `nutrition.js` — целевые КБЖУ (`TARGET`, `RANGE`), меню дня (`MEALS`),
  быстрый добор калорий (`EXTRAS`), закупки (`SHOP_M`, `SHOP_W`).

**Не подгоняй эти числа под «общепринятые» рекомендации.** Если цифра
кажется странной — она из программы, и менять её можно только по просьбе
владельца.

Структура цикла: недели 1–4 — Full Body (дни A/B/C), недели 5–8 — Верх / Низ /
Фулбоди, неделя 9 — разгрузка, дальше цикл повторяется. Модификаторы недели
считает `prescribe()` в `core/calc.js`: неделя 1 снимает подход и ставит
RPE 5–6, недели 7–8 добавляют подход к первым двум упражнениям дня, неделя 9
режет подходы вдвое и умножает вес на 0.9.

Прогрессия — двойная, реализована в `suggest()` (`core/history.js`): пока не
все подходы вышли на верх диапазона повторов, предлагается тот же вес и +1
повтор; как только вышли — вес растёт на `EX[id].step`.

Разгрузочную неделю определяет `isDeload()` в `core/calc.js` — один источник
правды и для `prescribe()`, и для `suggest()`. На ней `suggest()` не
прогрессирует, а предлагает вес на 10% ниже, округлённый **вниз по шагу
упражнения**: иначе −10% от 62.5 даёт 56.25, такой вес не набрать блинами и
раскладка штанги исчезает. Базой прогрессии разгрузочные тренировки не
становятся — `suggest()` отбрасывает их и считает от последней полноценной.
Без этого цикл после каждой разгрузки терял бы 10% навсегда.

## Договорённости

- Ванильный JS, без фреймворков и сборщиков. Если кажется, что нужен
  фреймворк — сначала обсуди: одна из целей проекта в том, чтобы
  опубликованная страница оставалась одним файлом без зависимостей.
- Цвета берутся только из токенов (`var(--...)`), литералов в компонентах
  быть не должно. Исключение — цвета соревновательных блинов в `PLATES`
  (`core/history.js`): это цветовой код IWF, он не зависит от темы.
- Блины считаются с точностью до сотых, а номинал печатается как есть
  (`String(p.w)`). Через `round1`/`fmtKg` блин 1.25 превращается в 1.3, и
  раскладка либо врёт, либо пропадает — так было на всех весах, где нужен
  блин 1.25: 27.5, 37.5, 42.5 и дальше через один.
- Строка подхода на экране тренировки живёт в замыкании над объектом
  черновика. Браузер шлёт `change` с поля ввода уже во время разборки DOM,
  когда `renderTrain()` пересобирает экран, — к этому моменту черновик
  может быть уже другим. Поэтому `commit()` сверяет, что его запись всё ещё
  принадлежит живому черновику, и молча выходит, если нет. Без этой проверки
  «Завершить тренировку» с активным полем повторов роняет `updatePlates`.
- Цифры набираются моноширинным: класс `.mono` или
  `font-family:'IBM Plex Mono'`. Шрифты: Archivo — интерфейс, IBM Plex Mono —
  данные.
- Палитра графиков проверена на цветовую слепоту: синий `--accent` и
  оранжевый `--series-2`. Добавляешь третью серию — проверь контраст пары
  заново, не бери цвет на глаз.
- Никаких графиков с двумя осями Y. Две величины разного масштаба — это два
  графика на общей шкале X (так сделаны «калории и вес»).
- После правки всегда `npm run build`. Дальше два адресата, и оба нужны,
  иначе версии разъедутся: публикация `dist/artifact.html` как новой
  версии того же артефакта (не нового) и `git push` — PWA уезжает на
  GitHub Pages сама через `.github/workflows/pages.yml`.

## Что стоит знать про публикацию

Артефакт уже существует, и вот его адрес:

```
https://claude.ai/code/artifact/9654fa0f-b2a1-40d4-a359-091d778c125f
```

**Публикуй `dist/artifact.html` только с этим `url`.** Публикация без ссылки
на существующий артефакт создаст второй, и дневник потеряет историю: база
привязана к артефакту, а не к файлу. Это верно и для новой сессии, и для
другой машины — URL берётся отсюда, а не из памяти.

Порядок обновления:

1. `npm run build`
2. прочитать артефакт по этому URL (`Artifact action:"read"`) — без свежего
   чтения живой версии публикация отклоняется, это защита от затирания
   чужих правок;
3. опубликовать `dist/artifact.html` с тем же `url`.

Объявленные возможности: `db` (хранение) и `downloads` (выгрузка CSV). При
переиздании их можно не перечислять — сохранённое объявление переносится.
Иконку (🏋️) при переиздании тоже не передавай: она закреплена за артефактом,
и смена иконки читается как другая страница.
